# AI Panel Studio · 产品需求文档（PRD）

> 状态：v0.1 草案（待评审）
> 阶段：SDD-1
> 一句话：用户给一个议题，系统现场"组一支虚拟专家局"，让观众在几分钟内围观一场有分歧、有追问、有收尾的圆桌讨论。

---

## 1. 产品定位

本地运行的 Web 应用。用户输入议题与专家人数（默认 4），系统调用大模型生成「1 位主持人 + N 位专家」的阵容（姓名、职业、Title、立场、专属颜色），用户确认阵容后进入演播厅，观看一场由 AI 实时推进的圆桌讨论。

**核心主张**：不是"多个 AI 分别回答同一个问题"，而是**一场有时间线、有发言权争夺、有观点演化的讨论**。价值来自"对抗性"和"过程可见"，而不是最终那段总结。

---

## 2. 目标用户与非目标

| 用户 | 诉求 | 对应设计 |
|---|---|---|
| 知识工作者 / 研究者 | 几分钟拿到多视角深度分析 | 阵容多样性 + 立场必须互斥 |
| 产品 / 决策者 | 预演各方立场与争议 | 分歧面板是主角，不是附录 |
| 教育 / 内容创作者 | 可复述、可回顾的访谈素材 | 完整 transcript 可回看 |

**非目标（本期明确不做，写进文档防止被追问）**

- 不做用户发言。用户是**观众**，只能围观，不能插话。（需求原文只写"加入观察已有讨论"）
- 不做登录 / 权限 / 多租户。多人同看靠"知道讨论 ID"即可。
- 不做语音 / TTS / 视频。文字演播厅。
- 不做讨论中途切换话题、暂停、人工干预。
- 不做移动端专门适配，但窄屏必须"合理分配区域"且不整页横滚。

## 3. 需求原文里没写、必须自己决策的 6 处

这一节是本 PRD 的核心。规格留白处，决策本身就是被考察的内容。

### D1 · 讨论何时结束

**决策**：双条件，先到先结束。

- **软条件（收敛）**：每轮结束后做一次收敛判定，若「新增分歧点 = 0」且「已覆盖 ≥ 3 个论点维度」，判定收敛。
- **硬上限**：`MAX_TURNS = 24` 轮（可配），防止不收敛的讨论无限烧。
- **无论何种结束都要落 `ended_reason`**（`converged` / `max_turns` / `degraded`），并且这句理由要显示在页面上。

**理由**：只写"主持人判断收敛"不可测；只写"固定 24 轮"就是机械结束，和"不允许机械轮流发言"是同一类毛病。

### D2 · 「自主决定发言顺序」如何做到可测

**决策**：把"自主"拆成两层——**模型提议，代码裁决**。

- 模型只负责产出：这个人此刻想干什么（`补充` / `反驳` / `追问` / `抛新论点`）+ 那 1-2 句话。
- 谁下一个说，由一个**纯函数选择器**决定，输入是当前讨论状态，输出是座位号。模型无权决定顺序。
- 纯函数天然可单测：给定状态，断言选中谁。这是整个项目最值得写测试的地方。

**理由**：把"涌现感"交给提示词、把"可测性"交给代码。两层分开，两个要求就同时满足。

### D3 · 共识 / 分歧的唯一真相源

**决策**：**只有一个 `consensus_state`，页面和总结都从它渲染。**

- 每 `K = 4` 条发言触发一次结构化抽取，产出带版本号的 `consensus_state`。
- 页面上的「实时共识 / 分歧」区直接渲染它。
- **主持人总结的 prompt 只注入这份 `consensus_state`，不允许自己重新"读一遍 transcript 再总结"**。

**理由**：同一个判断在两个地方各自生成，必然出现"面板说已达成共识、总结说仍有分歧"。这类同屏两套说法是最难被自己发现、却最容易被评委一眼看穿的缺陷。

### D4 · 「内部事件」的边界

**决策**：**举手 / 让位 / 准备发言只存在于状态事件，永不进入 transcript。**

- `event.type = panelist_state`（待机 / 准备发言 / 发言中）→ 只更新侧边小窗。
- `event.type = utterance` → 才进 transcript 表并渲染正文。
- 数据层就分开：`utterance` 表里根本没有"举手"这种记录，前端想显示也拿不到。

**理由**：靠前端"记得不要渲染"是纪律问题；靠表结构隔离是工程问题。选后者。

### D5 · 「各自独立视角」怎么理解

**决策**：解读为「**同一场讨论、各自一条独立的事件流连接**」，而不是"每个人看到不同内容"。

- 服务端为每场讨论维护一份事件序列（带单调递增 `seq`）。
- 每个浏览器各自订阅，`from_seq` 决定从哪开始补，断线重连不丢事件。
- 文档中显式写出这个解读，避免被当作需求误解。

### D6 · 仓库怎么交付

**决策**：**公开仓库 + zip 备份双份提交**。

- 需求写"GitHub/Gitee 邀请"，暗示私有仓库，但**对方账号名未提供**，邀请无法完成。
- 因此主路径用公开仓库（链接可直接访问），邮件另附 zip，两者内容一致。
- 如果后续拿到对方账号，再切私有 + 邀请。

## 4. 关键流程

### 4.1 主流程

1. 首页：进行中讨论列表 + "发起新讨论"
2. 输入议题、专家人数 → 生成阵容（展示姓名 / 职业 / Title / 立场 / 专属色）
3. 用户确认阵容 → 进入演播厅
4. 演播厅：主持人开场 → 专家自由发言 → 针对性交锋 → 主持人收尾
5. 结束后保留在同一页面，可回看完整 transcript 与最终共识 / 分歧

### 4.2 讨论阶段划分

| 阶段 | 目标 | 谁在说 | 退出条件 |
|---|---|---|---|
| `OPENING` | 主持人立框架、点名立场 | 主持人 | 1 条发言 |
| `EXPLORE` | 各方把观点摆出来 | 全员竞争发言权 | 每人至少 1 次发言 |
| `CLASH` | 针对前面的话追问 / 反驳 | 被点名者优先 | 分歧点不再新增 |
| `CLOSING` | 主持人收尾，讲清"还差什么" | 主持人 | 1 条总结 |

阶段推进同样由代码判定，不由模型自我宣布。

## 5. 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| A1 | 首页首屏 2 秒内出现内容，无白屏 | E2E 记录 FCP |
| A2 | 阵容生成含姓名/职业/Title/立场/颜色，立场互不重复 | 单测 + E2E |
| A3 | 连续 10 次发言中，同一人不超过 2 次连发，且非机械轮转 | 调度器单测（断言分布） |
| A4 | 每条发言 1-2 句，长度可断言 | 单测（字数上限） |
| A5 | 共识/分歧区在讨论过程中至少更新 3 次（不是结束后才出现） | E2E 抓版本号变化 |
| A6 | 页面文本中不出现 JSON 原文、不出现"举手"字样 | E2E 扫描 DOM 文本 |
| A7 | 两场讨论并行时，transcript 与共识互不串场 | 集成测试 |
| A8 | 1280 / 1366 宽下 `document.scrollWidth ≤ viewport` | 窄屏门禁脚本 |
| A9 | 模型不可用时讨论降级而非崩溃，`ended_reason=degraded` | 故障注入 |
| A10 | 结束后重进页面能完整回看 | E2E |

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 专家说话千篇一律 | 人设里强制"口语特征 + 反对对象"，并在测试中断言"串味"（A 的口头禅不出现在 B 的发言里） |
| 讨论退化成轮流念稿 | 选择器带冷却与权重，测试断言"轮转率"低于阈值 |
| 共识面板与总结打架 | D3 单一真相源 |
| 演示时模型超时 | 重试 1 次 → 该角色跳过并记事件 → 连续 3 次失败则降级收尾，绝不整场崩 |
| 文档与代码脱节 | 每阶段收尾强制回写文档，不留到最后统一写 |
