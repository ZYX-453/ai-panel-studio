# 核心 Prompt 记录

> 这份文档记录**真正用来驱动开发的 Prompt**，不是事后编的标准答案。
>
> 写作约定：每段固定五栏 —— **意图 / 约束 / 产出 / 挑战 / 如何修正**。
> 后两栏只写实测发生的事；某段没遇到挑战就写"没有"，不补戏。
>
> Prompt 文本为实际使用版本的整理：保留当时的约束与禁止项，删去与本项目无关的上下文，
> 不改变语义。

## 0. 工具链（如实记录）

| 项 | 实际使用 |
|---|---|
| 编码工具 | AI 编码助手（对话式 Agent，可读写文件、执行命令、跑测试） |
| 驱动模型 | DeepSeek-V4.1-Flash |
| 协作方式 | 人定方向与验收标准，AI 出实现；每一阶段结束后由人复核并决定是否进入下一阶段 |

**关于需求里的"Claude Code + Deepseek V4 Pro"**：作业说明的"重要规则"章节又写着"任意 Vibe Coding 工具"。
两处不一致时，这里选择**如实记录实际工具链**——评审看的是过程是否真实，编造一个没用过的工具风险更大。

人机分工的边界很明确：

- **人**：三个核心决策（结束条件、发言顺序、共识真相源）、验收标准、阶段放行
- **AI**：建模、写代码、写测试、跑命令、根据失败信息修
- **谁都不许**：一次性生成整个应用（需求明令禁止，也确实做不到——三十多个文件、四层边界、一条真实事件流，一次性生成的产物没有一处可验证）

## P1 · SDD｜数据模型：ER 图 + SQLite DDL

**意图**
把"圆桌讨论"这个业务落成可约束的表结构，而不是先写代码再补库。

**约束（逐条写进 Prompt）**
1. 只产出 `db/schema.sql` 与 ER 图说明，**不写任何应用代码**
2. 内部状态（举手、准备发言、待机）**不得**成为 `utterance` 的列或值
3. 共识与分歧必须是**单一真相源**：页面和收尾总结都从同一份数据取
4. `FINISHED` 状态必须有结束原因，用数据库自己守住，不靠应用层自觉
5. 同一场讨论内，座位、颜色、立场三者各自唯一

**产出**
6 张表：`discussion / panelist / utterance / consensus_state / consensus_snapshot / event`，
外键全部带 `ON DELETE CASCADE`，`event(discussion_id, seq)` 唯一，`utterance(discussion_id, seq)` 唯一，
外加一个触发器：`status='FINISHED'` 且 `ended_reason IS NULL` 时直接 `ABORT`。

**挑战（实测）**
第一版把"谁在准备发言"也做成 `utterance` 的一个字段（意图是"这样前端一次就能拿到"）。
这正好踩中约束 2 —— 一旦内部状态进了 `utterance`，侧边小窗和正文就成了同一张表的两列，
后面必然出现"某条举手被渲染成一句发言"。

**如何修正**
删掉该字段，明确"内部状态只能走 `panelist_state` 事件"。
这条约束后来在 `engine._emit_state()` 里落成物理边界：那个函数只会写 `panelist_state`，
**没有能力**顺手写进 `utterance`。不是靠纪律，是靠没有那个代码路径。

## P2 · SDD｜API 契约与 SSE 事件类型

**意图**
在写任何一行 Python 之前，先把"前端能收到什么"钉死。

**约束**
1. HTTP + SSE，**不要** WebSocket
2. 必须写清断线重连：谁带 `Last-Event-ID`、服务端从哪一帧补
3. 统一信封 `{ok, data}` / `{ok, error}`，前端只写一次错误分支
4. 事件类型要能覆盖：阶段、专家状态、发言、共识、结束、单次失败
5. 保活**不能**伪装成业务事件
6. 每个端点给出错误码表，含 HTTP 状态

**产出**
8 个端点、7 类事件、5 个错误码。其中三条是刻意设计：
- `id:` 用事件序号，`utterance_seq` 单独一个字段（第几句 ≠ 第几个事件）
- `ping` 以 SSE 注释行发出，不占 seq、不入库
- `panelist_state` 与 `utterance` 是两条渲染路径，永远不混

**挑战（实测）**
两处都出过问题：
1. 初版把 SSE 的 `id` 和发言序号都叫 `seq`，前端把事件序号当"第几句"，"回应第 5 句"指错人。
2. 初版 `ended` 事件顺手带了 `consensus_version`，于是"共识版本"有了两个来源。

**如何修正**
- 前者改成 `utterance_seq` / `reply_to_utterance_seq`，并写一条**断言两者不相等**的前端用例。
- 后者删掉冗余字段，并加 `backend/tests/test_event_shape_parity.py`：
  运行时与样例数据两个来源的 payload 字段集必须**逐字相同**。
  这条测试在后续改动里真的拦住了两次分叉。

## P3 · DDD｜组件树 + 设计 token + 三区布局

**意图**
让界面的"职业感"来自结构与排版，而不是靠装饰。

**约束**
1. **整页不滚动**，三个区（专家席 / 发言 / 共识）各自独立滚动
2. 每位专家一个专属色，色值要过对比度检查（正文对比 ≥ 4.5:1）
3. 窄屏（<1100px）三区变页签，同一时刻只显示一个
4. 不引 UI 组件库、不引图表库、不引路由库
5. 空态必须先做好：**值为 0 时显示 0，不许渲染成空白**
6. 内部状态只出现在侧边小窗，绝不进正文

**产出**
三页（首页 / 阵容确认 / 演播厅）+ 六个组件 + 一套 CSS 变量 token。
`grid-template-rows: auto auto 1fr` + `.pane { min-height: 0 }` 实现三区独立滚动。

**挑战（实测）**
1. 初版用整页滚动，专家席跟着正文一起走，滚到第十句时看不到谁在说话 —— 直接违反约束 1。
2. 确认页"返回列表"按钮被 grid 拉满整行（默认 `align-items: stretch`）。
3. 窄屏下表格/长标题把页面撑出横向滚动条。

**如何修正**
- 布局改成 `100vh` 的 grid + `min-height: 0`，三区各自 `overflow-y: auto`；
  这条后来用门禁脚本卡住：`scrollHeight > clientHeight` 就算不通过。
- 按钮单独放进 header 区域并显式宽度。
- 加 `scripts/check_ui.py`，在 1440/1366/1280/1024 四个宽度断言 `scrollWidth ≤ innerWidth + 1`。

## P4 · TDD（红）｜只写调度器测试，禁止写实现

**意图**
把"谁该发言"从模型手里拿回来，并且先证明"这样做是错的"。

**约束**
1. **只写测试，不写实现**，要求此刻全红
2. 禁止顺手实现（这是本轮最容易破的一条）
3. 必须覆盖：不连续点名同一人、必须回应上一条、阶段内发言分布、冷却窗口
4. 测试只依赖纯函数签名 `pick_next(seats, turns, phase, seed)`，不碰数据库、不碰模型

**产出**
`backend/tests/test_scheduler.py`，38 条用例，此刻全红。

**挑战（实测）**
AI 确实想"顺手把实现也写了"。拦下来的方法是把禁止项写成第一行硬约束，
并在它的产出里检查：**只要出现实现文件就算这一轮失败**。

更麻烦的是第二轮：补上实现后 38 条全绿 —— 但真实跑起来是**严格轮转**
（12 轮里每人恰好一次），完全没有"抢话"的感觉。测试通过不等于行为正确。

**如何修正**
加一条"默认路径不许机械轮转"的回归用例，先让它红。
然后给调度器加两样东西：话题相关度 `_affinity()` 与抢话倾向 `eagerness`，用稳定哈希做抖动（同 seed 可复现）。
40 条绿之后再看真实输出，才出现"同一人被连续追问"这种像讨论的形态。

**这一轮是最有价值的一轮**：它证明"测试绿了"和"行为对了"是两件事。

## P5 · TDD（绿）｜按测试实现，禁止改测试

**意图**
在已有测试的约束下把实现补齐，且不许动验收标准。

**约束**
1. 只改实现，**不许改测试**（包括"放宽断言""换个预期"）
2. 不许新增依赖
3. 每次只推进一组（调度 → 人设 → 共识），绿了再下一组
4. 每次跑完必须贴出真实数字（多少条通过）

**产出**
调度器（40 条）、人设装配（prompt 必须注入立场与攻击面，且不得复述他人）、
共识（Jaccard 判重、旧分歧不消失、**版本只在内容变化时 +1**）。

**挑战（实测）**
共识这块出过一次"版本虚增"：每轮抽取都 +1，哪怕内容一模一样。
表现是共识面板从 v1 跳到 v5 但内容没变，看起来像在疯狂更新。

**如何修正**
把"版本递增"改成"内容变了才递增"，并在测试里钉死：
同一份 points/disputes 连续抽取两次，`version` 必须保持。
这条后来也解释了为什么 `ended` 事件里不该再带一次版本号 —— 版本只有一个出口。

## P6 · E2E｜真实跑一场，逐条断言

**意图**
证明"整条链路真的能跑完一场讨论"，而不是"接口都返回 200"。

**约束**
1. 必须真实调用模型，不许用预置内容
2. **不以 HTTP 200 作为通过标准**
3. 必须验证断线重连：中途断开、带 `Last-Event-ID` 接上，收到的事件不重不漏
4. 必须验证纪律：内部状态词不得出现在正文；回应关系必须指向更早的发言
5. 必须验证收敛：最后一条是 `ended`，`ended_reason` 在允许集合内，快照与流能对上

**产出**
`scripts/e2e_run.py`：创建 → 确认 → 开始 → 断线 → 重连 → 读到底 → 快照对账 → 导出对账，
二十余条断言，失败打印 `★`，`EXIT=0 且 ★=0` 才算过。

**挑战（实测）**
1. 第一版脚本只断言"有 ended 事件"，结果**主持人独白**（开场后一直在自己说话、永不开专家）也能过 —— 因为它确实最后结束了。
2. `OPENING` 阶段的第一帧 `phase` 事件在新场次里根本没发出来（初值直接设成了 `OPENING`，所以"没有变化"）。
3. 序号从 0 起导致补发时首帧被过滤（见 P2 修正）。

**如何修正**
- 加"发言数 ≥ 6""阶段不得连续重复""每条发言前后必须有状态事件""回应必须指向更早的发言"等断言，
  主持人独白那条立刻红，删掉 `elif phase == "OPENING"` 分支后转绿。
- `OPENING` 初值改为空，让第一帧真实发出。
- 序号两侧统一从 1 起。

**再一次验证了同一件事**：断言写得松，绿灯就是装饰。

## 系统 Prompt 四则（产品运行时，不是开发过程）

这四段是**运行期**真正发给模型的系统提示，来源是 `backend/app/personas.py`。
它们与上面的开发过程无关，但同样属于"这套系统的核心 Prompt"，所以照实贴在这里。

这四段的约束是**互相排斥**的：专家要站定立场不许改口，主持人恰恰要中立；
如果四段长得像，说明角色根本没分开。所以 `personas.py` 只拼字符串、不调模型 ——
"prompt 里到底写了什么"可以被单测直接断言，串味、漏写限制在测试阶段就能拦住。

### S1 主持人（`build_host_prompt`）

```
你是「{name}」，本场圆桌的主持人。

【你的定位】{stance}
【讨论议题】{topic}
【当前阶段】开场 / 各方陈述 / 交锋 / 收尾

【你的职责】
- 不预设立场，不替任何一方说话。
- 追问、串联，点出谁在回避问题。
- 允许尖锐，但不要人身攻击。

【最近发言】
第3句 周敏：……
第4句 许巍：……

【本轮任务】按阶段只给一条，四阶段互斥：
- 开场：用一句话把议题收成一个能用「该」或「不该」回答的子问题，再点名请一位专家先给最关键的那一条理由。
  不要一次抛出多个问题 —— 议题写得越大，越要先切出一条能在二十句内谈完的；
  但也不要把它缩得没人关心（「该不该讨论这个议题」这种等于没切）。
- 各方陈述：（不给任务，这一段就该让各方把话说完，主持人只点名不推进）
- 交锋：先判断场上是不是在同时讨论两件事。如果是，点明「这是两个问题」，
  要求大家先把第一个谈完、另一个记下来另说；如果不是，就追问最含糊的那一句。
  只有真的跑题了才收 —— 每轮都套这个句式会打断正常的交锋。
- 收尾：请做收尾总结：说清哪些已经达成共识、哪些仍然悬着、下一步该做什么。
  不要引入新的论点，也不要假装全场已经统一。

【硬性规则】
1. 只说 1-2 句，不超过 60 字。宁可少说，不要把话讲满。
2. 直接输出你要说的那句话本身。不要输出 JSON、不要加引号、不要写「某某说：」。
3. 不要提到自己在扮演角色，也不要提到 AI、模型、提示词。
4. 你总结的内容必须与给定的共识/分歧清单一致，不得新增判断。
```

**四阶段的任务是互斥的，一条都不能串到别的阶段去。** 加"收窄子问题"那段时，
一次误编辑让收尾任务落进了 `elif CLASH` 分支，于是交锋阶段同时收到
"点明这是两个问题"和"做收尾总结"两条互斥指令 —— 而当时 115 条测试全绿，
没有一条在看 prompt 本身。现在由 `test_host_prompt_has_exactly_one_task_per_phase`
按阶段断言"有且仅有一条【本轮任务】"，注入复现那次误编辑会红。

### S2 专家（`build_expert_prompt`，模板 + 人设变量）

```
你是「{name}」，正在参加一场圆桌讨论。

【你的立场】{stance}
【你的关注点】{focus}
【你的说话习惯】你习惯这样开口：「{catchphrase}」。保持这个语气，但不要每句都用同一句开场白。
【你最想推翻的说法】{target}
　　—— 这是你上场的理由。场上只要有人说出接近这句话的判断，就点他的名直接反驳，
给一个具体反例或数字；如果暂时没人这么说，你就把它当靶子主动抛出来，
写成「有人会说……」，然后当场拆掉它，逼对方接话。

【讨论议题】{topic}

【最近发言】
第5句 林雪：……
第6句 许巍（你）：……

【你要回应的对象】许巍（第 6 句）—— 直接针对那句话讲，不要绕开。

【你刚才说过的】这几句已经说过了，不要换个说法再讲一遍：
第5句 你：……

【硬性规则】
1. 只说 1-2 句，不超过 60 字。宁可少说，不要把话讲满。
2. 直接输出你要说的那句话本身。不要输出 JSON、不要加引号、不要写「某某说：」。
3. 不要提到自己在扮演角色，也不要提到 AI、模型、提示词。
4. 不要复述或概括别人刚说过的话，直接给你的判断。
5. 不要因为别人反对就改口。你可以被说服，但要给出理由。
6. 不要重复你自己已经说过的判断，每一轮都要往前推进一个
   新的细节、具体场景或数字。
7. 不要借用别人刚用过的关键词和比喻，用你所在领域里的词说同一件事。
8. 不要每轮都走「先肯定对方、再转折」这条路，更不要开头就写「我认」。
   直接给判断，理由放在后面。
```

下面两段**不是常驻**，只在代码判定条件成立时追加。常驻等于永远在提醒，
模型只会把它当背景噪音；按条件给才有信号量。

```
【重复预警】你上一句与场上已有发言几乎一样。换一个具体案例、数字或场景重说，
换掉原来的措辞，不要只改开头两个字。
```
触发条件：新生成的那句与场上任何一句**连续 12 个字相同**（`content.is_repeat`）。
重说一次之后仍然撞车就保留新那句 —— 宁可内容一般，也不要让这一轮空着。

```
【这一轮的要求】场上已经连着几句都在互相补充、没人反对了。
你必须指出一个具体的反例或代价：按刚才那个做法，在什么情况下会失效、
谁会因此受损，说一件具体的事。
```
触发条件：`CLASH` 阶段，且最近三句都不是「反驳」也不是「追问」。

**这两段为什么必须由代码插，而不是写进系统提示常驻**：
模型看不见自己的完整历史（窗口只有 6 句），也不知道"最近三句有没有人反对"；
这两件事代码一眼就能算出来。让模型判断"我是不是在复读"，等于让它凭记忆答一道
只有外部观察者能答的题。

**`【你最想推翻的说法】`这一栏在 11-20 被整个换过，原因值得记一笔。**
原来叫 `attack`，存的是"这个角色容易怎么跑偏"（例如"用自己公司的规模套所有人"），
prompt 里写「注意不要在这里翻车」。方向是反的：模型读到这句话只会**自我审查**，
不会去攻击别人。8 场真实运行里 24 句几乎全是互相补充，`intent` 统计里「反驳」
不到一成，就是这条指令的直接后果。

现在 `target` 存的是**一句别人可能真的会说出口的断言**，并且带引号：

| 角色 | 旧 `attack`（元标签） | 新 `target`（可反驳的命题） |
|---|---|---|
| 周敏（教授） | 用个案代替普遍规律 | 「远程只是把工位搬回家，沟通并不会变少」 |
| 许巍（CTO） | 拿自己公司的规模套所有人 | 「物理距离决定协作质量，远程注定伤效率」 |
| 林雪（顾问） | 把复杂问题拖进分类学 | 「远程是公司级开关，要么全开要么全关」 |

差别在于**可被反驳**：你可以举一个"沟通量没降但创新降了"的研究去打第一条，
却没法"反驳"第二条里的"用个案代替普遍规律"——那是对人的评价，不是对事的判断。

配套的代码约束有两条：
1. `lineup.validate()` 增加靶子互斥检查（相似度 ≥ 0.6 判重合），
   防止两位专家打同一个靶子——那看起来像交锋，实际是齐射。
2. 靶子为空时**整段不渲染**（模型偶尔漏字段），不留一个空靶子让模型自己编。

### S3 共识抽取（`build_consensus_prompt`）

```
你是这场圆桌讨论的记录员。唯一任务是把讨论整理成结构化的共识与分歧。

【讨论议题】{topic}

【最近发言】
（最近 10 句）

【输出格式】严格输出一个 JSON 对象，不要输出任何其他文字：
{"points": ["已达成共识的结论"], "disputes": ["仍存在的分歧"],
 "resolved": ["已经谈拢的那条旧分歧的原文"], "based_on_seq": 12}

【规则】
- points 写**多方已经明确认同的结论**，不必是谁的分歧被解决了。
  只要场上不止一个人表示认可，就写进来（例：「需要有人落笔记录」）。
  但不要把某一方单方面的观点写进来充数。
- disputes 写成「一个悬而未决的问题」，而不是「某人不同意」。
- disputes 只记**立场层面**的对立：谁认为该怎样、谁认为不该怎样。
  不要记「由谁核实」「用什么工具」「怎么归档」这类执行细节 —— 那是讨论的
  延伸话题，不是分歧。把它们记成分歧，条目会越滚越多，讨论永远收不了口。
- 之前已经存在、这次发言没有推翻的分歧，必须原样保留；不要因为这次没被提到就删掉。
- 某条旧分歧谈拢了：把谈成的结论写进 points，同时把那条分歧的**原文**写进
  resolved（逐字照抄上面【仍未解决的分歧】里的那一行）。没谈拢就是空数组 []。
  resolved 找不到对应原文时会被忽略，不要为了凑数硬填。
  resolved 和 points 是两件独立的事：没有旧分歧被解决，points 照样可以有内容。
- 讨论超过 15 句时，points 通常至少有 1 条；确实一条都没有才写 []。
- 每条不超过 30 字。
- based_on_seq 必须填本次抽取所依据的最后一句的序号。

【已有的共识与分歧】
【已达成共识】
- （上一版 points，逐条一行）
【仍未解决的分歧】
- （上一版 disputes，逐条一行）
```

**11-20 的改动：加 `resolved`，并把旧状态分区传进去。**

原来分歧想消失，只能靠"与某条新共识相似度 ≥ 0.5"被动移除。但分歧写
「周报该不该取消」、共识写「周报不必当唯一载体」，措辞天生不同，这个门槛
永远够不到 —— 实测一场 2 人讨论，24 句里分歧**恒为 6 条且在增长**，
而 D1 的收敛条件是"连续两版零分歧"，那条路径数学上不可能走到。

现在给了模型一条显式通道（`resolved`），代码仍握裁决权：只在相似度 ≥ 0.9
时逐条删除，模型抄错半句就失效，凭空编一条也不会误删任何东西。
旧状态也从"points 和 disputes 混成一坨"改成两段分开 ——
模型要**逐字**引用某条旧分歧才填得对 resolved，混在一起它只能概括，概括的匹配不上。

**这里也踩了一个自己的坑**：加了 `resolved` 之后，模型把 `points` 理解成
"只放已解决的分歧"，导致整场 7 个版本 `points` 全空，E2E 的
"末版 points 非空"断言当场报红。是文案歧义，不是代码问题 ——
补了"resolved 和 points 是两件独立的事"和"超过 15 句通常至少有 1 条"之后，
同一上下文连抽 3 次都稳定给出共识。

**为什么允许这一段输出 JSON，而专家段明令禁止**：专家的话要直接上屏，带结构就是脏数据；
抽取结果是给程序用的，必须结构化。同一句"禁止 JSON"不能套在两个用途上。

**"必须原样保留未消解的分歧"这条是踩出来的**：初版没有这句，模型倾向于把"这次没提到"当成"已经解决"，
于是分歧越抽越少，最后一版共识看起来天下大同。

### S4 收尾总结（`build_summary_prompt`）

```
你是「{name}」，本场圆桌的收尾人。

【讨论议题】{topic}
【总结所依据】第 10 句为止的共识记录（v3）

【已达成的共识】
- ……
【仍未解决的分歧】
- ……

【硬性规则】
1. 只能使用上面列出的内容，不得引入新论点、新数字、新人物。
2. 分歧为零时可以说已经收敛；但不要因此夸大成「取得一致意见」——
   共识条目各自的边界仍要交代清楚。
3. 4-6 句，直接说结论，不要「感谢各位」这类客套。
4. 不给行动建议清单，除非共识里已经明确写了。
```

**这段 prompt 刻意不传 transcript。** 总结只允许基于 `consensus_state` 写，
因为同一份 consensus 也在页面上渲染成共识面板 —— 如果总结另读一遍原文，
就必然出现「面板说已达成、总结说仍有分歧」。这是本作品对"同屏两套口径"唯一可行的根治办法：
不是靠纪律要求两处写一致，而是让它们**物理上只有一份可读的输入**。

---

## 附：这些 Prompt 的共同点

1. **每条约束都可验证**。"写得专业一点"没法验，"不超过 60 字"可以。
2. **禁止项比要求项更重要**。模型天然会做加法（多写、多列、多带字段），
   所以最有效的约束形式是"不许……"，且写在最前面。
3. **不允许模型决定状态**。结束、轮次、共识版本全由代码裁决，
   模型只负责生成文本 —— 这是整个项目最重要的一条边界。
