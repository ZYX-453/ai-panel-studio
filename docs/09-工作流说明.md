# 开发过程思路与工作流说明

> 对应交付物要求第 3 项。1-1.5 页。

## 一、实际用的工具链（如实记录）

作业写的是"Claude Code 结合 Deepseek V4 Pro"，同页的"重要规则"又写"任意 Vibe Coding 工具"。
我实际用的是 **WorkBuddy（Vibe Coding 工具）+ DeepSeek 对话模型**，没有用 Claude Code，
也没有用 V4 Pro。工具链按实际情况写，不编造 —— 评审看的是过程是否可追溯，不是工具名字对不对。

模型这一点上有过教训：开发早期只跑了单元测试就认为"跑通了"，
后来换到真实密钥才发现**事件序号从 0 开始**，导致前端重连时漏掉第一帧。
单测里没有一条能发现它，因为假模型根本不产生真实的 SSE 流。

## 二、开发流程：四个阶段，每层的职责是"发现上一层的错"

```
SDD 文档  →  DDD 界面  →  TDD 代码  →  E2E 真实跑测
（想清楚）   （看得见）    （钉住行为）   （验真）
```

**1. SDD（数据建模 + API 契约）**
先把 PRD、ER 图、API 文档、UI 稿写完，评审通过才写第一行代码。
这一步最大的收益不是"文档好看"，而是**把歧义提前暴露在纸上** ——
比如 `seq`（事件序号）和 `utterance_seq`（发言序号）是两套编号，
如果不先写成契约，代码里一定会混用。

**2. DDD（组件树 + 设计 token + 三区布局）**
先定 `types.ts` 的形状，再写组件。前端只做一件事：`applyEvent(state, event)` 是唯一写入口。
这条约束让"直播、断线补发、回看"共用一条管线 —— 结构上不存在"直播有、回放丢"的缝。

**3. TDD（红 → 绿）**
先写测试再写实现，且**测试必须能红**。每加一条判据，我都会把被守护的那行代码临时改坏，
确认用例失败，再还原。这个习惯抓到的真缺陷不少于五处：
`converged` 忘带"必须进过交锋"（第 10 句就收尾）、`resolved` 通道被注释掉却全绿、
补抽逻辑去掉后无一场报错 —— 全部是"注入→红"才暴露的。

**4. E2E（真实模型跑完一整场）**
这一步不能省，也不能用单测代替。项目累计 **25 场**真实跑测（19 场撞 24 轮上限、
4 场自然收敛、2 场降级），每场跑完断言二十余条：`seq` 连续、发言前后有状态事件、
内部状态词不进正文、回应指向更早的发言、收尾事件必须是最后一条。

## 三、三个典型问题，以及怎么解决的

**① 一屏写着"交锋"，22 句里 18 句是"补充"**
原因是"意图"由调度器猜（它只知道谁被点名、谁连说了两句），而不是由说出来的话决定。
改法：`classify_intent()` 从正文反推意图，调度器的 `intent_hint` 不再参与。
改完第一版又漏判 —— 关键词表只认"不同意/站不住"，而新 prompt 派生的是"有人会说 X，那我举个数"。
**这是同一类错误的第二次：改了行为，没改度量。**

**② 人设写成了"自我审查条款"，讨论变成互夸会**
`attack` 字段存的是"这类人容易犯的错"，prompt 里写「注意不要在这里翻车」——
模型读完只会小心别犯错，不会去攻击别人。8 场真实运行，24 句里反驳平均不到 2 句。
改法：字段语义换成 `target`（别人可能真会说出口的断言），prompt 换成进攻指令：
有人说出接近这句话的判断就点名反驳，没人说就自己抛出来当靶子。
效果：靶子句式从旧 11 场的 0 次变成每场 5 次，反驳 6-8 句。

**③ 收敛分支在数学上不可达**
跑 4 场 2 人小阵容，一场都没 `converged`。查库发现分歧从第 4 句起恒为 6 条且在增长：
`merge()` 对分歧只累加、上限只管共识；而一条分歧想消失，只能靠"与新共识措辞相似度 ≥ 0.5"，
可分歧写"周报该不该取消"、共识写"周报不必当唯一载体"，这个门槛永远够不到。
改法：给模型一条显式通道 `resolved`（逐字引用旧分歧），代码按 0.9 阈值裁决；
另外把收敛条件从"连续两版零分歧"放宽为"分歧连续两版不增且 ≤ 1"。
**这是放宽判据，不是修好了 bug** —— 代价写在 08 文档里，没有粉饰。

## 四、我对"工程化 AI 开发"的理解

三句话：

**1. AI 写代码的速度，已经把"判断对不对"变成了瓶颈。**
这个项目里几乎所有真缺陷，都不是 AI 写不出来，而是它写出来了、测试全绿、文档也写得很像样，
但真实跑一遍才发现不对。最典型的一次：整场 24 轮全是主持人独白，
而 72 条测试全部通过 —— 因为没有一条在检查"到底有没有别人说过话"。

**2. 所以流程的价值不在"让 AI 写得快"，而在"让错误尽早暴露"。**
文档暴露歧义，契约暴露命名分叉，测试暴露行为偏差，真实跑测暴露"测试本身没测到"。
四层每一层的职责都是**发现上一层的错**。缺一层，错误就会以"看起来正常"的形态进入交付物。

**3. 最终防线是"不要相信任何自述"，包括 AI 的、测试的、文档的。**
判断标准只有一条：把被守护的那行代码改坏，看它会不会红。不会红的用例宁可不写。
这次还多学了一条 —— **测试数量本身也是口径**：`test_engine.py` 里 8 个 `def test_`
其实只有 4 个名字，每组都有一份从未执行过，而 pytest 一直报"全绿"。
判别不需要跑测试：`grep "^def test_" | uniq -d`。

一句话总结这个项目的工作方式：**先想清楚，再让 AI 写；写完不算数，跑一遍才算数。**
